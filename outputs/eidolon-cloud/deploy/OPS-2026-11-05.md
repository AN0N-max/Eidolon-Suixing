# 运维启动修正 2026.11.05.1

用户实际服务器截图确认：预检和接管前备份成功；service 文件已加载，但 MainPID=0、inactive/dead、开机启动 disabled。运行 journalctl 返回 No entries。不能把它写成服务启动成功，也不能仅凭无日志认定某个唯一根因。

修复：只有初始状态为 failed 才调用 reset-failed，避免对 inactive 服务执行非必要的前置重置；systemctl 的失败命令、返回码与有界错误文本会反馈到本机终端；激活失败保留原始原因，停止清理失败不再覆盖它，也不会未经确认就声称服务已停止；就绪超时保留最后一次错误及 systemd 状态。

这是已定位的脚本流程与诊断缺陷修复。inactive 服务可能在 systemd 中被回收，因此无条件重置可能在 start 前失败；当前没有取得服务器该步骤的原始 stderr，尚不能确认它解释了全部现场问题。依据：[systemctl](https://freedesktop.org/software/systemd/man/latest/systemctl.html)。

原 unit 内容与安全限制保持，兼容前一版已安装且未修改的 unit。数据库、备份、源码包、私网、模型和语音逻辑不改。新脚本以 eidolon-cloud-setup-20261105.py 交付，不覆盖上一版。

新增 4 项模拟回归：inactive 服务不重置即可启动；failed 服务先清除失败；无 journal 时仍显示控制命令错误；清理失败仍保留原启动错误。连同此前检查，部署测试 31 项通过；全套框架与实际 Java 桥接合计 52 项通过（具体运行记录见本地交付状态）。systemd 控制仍为模拟，不能替代服务器验收。

运行新版 service-install 将重试已核验 unit 的接管、健康检查与启用开机启动；不会重装依赖、恢复数据库或重启服务器。成功后再运行 status 与 backup。如仍失败，保存新版显示的具体错误，按该错误处理；不要反复重装或放宽整个服务安全限制。
