# 主动搭话 · 1.3

1.3变更：使用实际生成任务判断忙碌，不再因残留chatBusy永久跳过；生成中、近期交流、等待回复、暂时不合适的作息等条件在原有效期内延后检查。只有真正请求模型才占请求预算；到期不补发。完全相同的配置保存、弹窗/通知样式修改保留任务，实际分配规则变化才替换未执行计划。

按今日已发送次数更少、距上次主动消息更久的角色优先分配；相同时使用每日稳定顺序。每位角色同时最多一条安排，同一条用户消息最多开启一轮机会，不为了凑满每日上限反复排同一人。用户回复后可在上限内获得后续机会。仍须先有用户聊天、满足角色范围/关系/免打扰/作息等条件，不能保证每位角色每天都有计划。旧版多次重复安排在首次升级时替换一次，已完成消息与调用次数保留。

今日计划先展示当前安排，执行和失效记录折叠；另可查看各角色当前筛选说明。说明反映当前条件，不倒推历史原因。详见[1.3发布记录](RELEASE-1.3.md)。以下调度基础仍沿用1.2，后方1.0说明仅作历史记录。

1.2调度基础与原验收范围见[RELEASE-1.2.md](RELEASE-1.2.md)。

- 每日约05:00做本地计划；原关系/间隔/指定时间决定最早窗口，角色作息、空闲及免打扰决定可用时段，在当天未来窗口随机安排。指定时间模式使用目标时间后的15分钟窗口，已经错过则当天不补。最早计划在检查后5分钟；无合适时间可为空。
- 仍只向有用户聊天且符合活动天数、关系和会话条件的角色搭话。一条未获用户回复的主动消息会阻止后续主动发送；送礼不算回复。
- 统一上限可逐角色覆盖，支持限定角色范围。新增计划最小间隔默认30分钟（15–240）、最近交流暂停默认30分钟（5–1440）、有效期默认90分钟（15–240）。全局每日消息与请求预算保留。
- AlarmManager只保留最近一个非精确唤醒，WorkManager负责持久后台工作与网络条件。应用内周期检查只请求核对计划；旧后台周期和失败自动重试参数留在本机配置兼容，但1.2不再使用它们触发请求。
- 网络未恢复时等待；已发出请求后的失败/中断不自动重发，今日计划可手动重试，每任务最多三次；仍占每日请求额度。旧任务/旧回答由版本与数据库状态阻止落库。
- 日程改变会检查待执行任务，不合适的时段标为跳过，可手动重新安排；不会改已完成消息。配置改变、重新安排只安排今天未来任务，保留已发送消息及请求计数。
- 主动消息系统通知有独立开关，隐私模式隐藏系统通知正文；悬浮提示仍由已有权限和样式控制。正在对应聊天不弹窗，其他页面横幅，应用外悬浮窗/通知。未读独立保存，不依赖系统是否允许通知。
- 原1.0的15分钟周期不是当前实现；没有常驻主动服务，也没有精确闹钟权限。OriginOS冻结、Doze、重启、最近任务清理和强行停止的限制仍须分别验收。

# 主动搭话 · 1.0

入口：设置 → 提醒与后台 → 主动搭话。页面分为五个可折叠板块。默认不开启，设置和预览不调用模型；实际搭话使用用户配置的聊天接口。

## 频率与对象

| 参数 | 默认 | 范围或选项 |
| --- | --- | --- |
| 触发方式 | 按关系随机间隔 | 关系、固定间隔、每天固定时间 |
| 固定间隔 | 12 小时 | 0.25–720 小时，支持小数 |
| 每天固定时间 | 12:00 | HH:mm，按搭话时区 |
| 每日总消息上限 | 3 条 | 1–30 |
| 单角色每日上限 | 3 条 | 1–30 |
| 每日搭话请求上限 | 10 次 | 1–100 |
| 最近有聊天活动 | 7 天 | 1–365 |
| 最低好感 | 40 | 0–100 |

总上限、单角色上限和请求上限共同生效。请求计数在API请求前持久化；失败、取消和被新设置废弃的请求也消耗次数，保存设置不清零。请求计数不因时钟回退而重置；按所选搭话时区的新日期恢复额度。消息上限按本地保存的主动消息计数。普通聊天、判断、记忆提取不由这个搭话请求额度控制。

只向已经有用户聊天的角色触发；一条主动搭话发出后继续等待用户回复。送礼不会解除这个等待。最近聊天活动沿用会话的更新时间。会话结束、关系冷却、睡觉、洗澡，以及有正式待回复消息的角色继续暂停。

## 各关系阶段间隔

| 阶段 | 默认最短–最长 | 可设置范围 |
| --- | --- | --- |
| 信任及以下 | 20–36 小时 | 各0.25–720小时 |
| 亲近 | 8–16 小时 | 各0.25–720小时 |
| 亲密 | 3–6 小时 | 各0.25–720小时 |

只有关系随机模式使用这三个区间。沿用现有好感分档（65/85），不改变角色关系进度。最短不能大于最长。

## 时区与免打扰

默认搭话时区为Asia/Shanghai，可填有效IANA时区，例如Asia/Tokyo、America/New_York。每天定时、日额度边界和搭话免打扰都用这个时区；独立于档案时区，避免升级改变原先北京时间安排。

免打扰默认开启，22:00–08:00，支持跨午夜或同一天的时间段。开始和结束不能相同，全天允许应关闭开关。间隔落在免打扰内会顺延到结束，再随机错开0–120分钟；错开上限可设0–240分钟，不会重新进入下一段免打扰。每天定时默认可在任意时刻触发，另有“每天固定时间也遵守搭话免打扰”开关。

固定计划及其随机结果持久保存，后续检查不会重新随机。每天定时首次检查以最后聊天活动为锚点，因此不会仅因检查晚了几秒而跳过今天。失败后的重试时间也复用已保存计划。

## 后台检查与生成

| 参数 | 默认 | 范围 |
| --- | --- | --- |
| 应用内检查间隔 | 60秒 | 15–3600秒 |
| 后台检查间隔 | 15分钟 | 15–1440分钟 |
| 最多参考历史消息 | 30条 | 4–100 |
| 最多引用记忆 | 3条 | 0–20，0表示不引用记忆 |
| 失败后重试间隔 | 0分钟 | 0–1440，0表示按原搭话间隔等待 |

实际请求仍受原有约24000字的历史上下文裁剪。扩大上下文会增加费用。后台使用持久化周期JobScheduler；15分钟是系统最小配置间隔，不能保证准点、最长延期或强制停止后的运行。多个角色到期仍逐个检查，不并发大量请求。

保存设置会取消正在执行的旧搭话、递增设置版本并重新安排尚未发送的搭话。旧回答即使晚返回也不能写入聊天。投放事务会再次检查版本、总额度、单角色额度、最新消息、等待正式回复、关系和作息状态。

OriginOS真机调试曾记录fast_freezer冻结整个应用，即使短时前台服务运行也会停顿。用户将Eidolon从“智能控制后台耗电”改为“允许后台耗电”后反馈成功。设置页提供“打开应用后台设置”：应用信息 → 电量 → 后台耗电管理。冻结不是弹窗尺寸或免打扰参数能修复的，不自动修改全局系统策略。

## 弹窗与提示

宽度240–420dp，默认340；顶部/中部/底部，左侧/居中/右侧；停留2–60秒，默认6.5秒。提示音和振动各有开关，并遵守手机静音、免打扰和通知权限。这些共享外观设置也用于正式回复提醒。短时回复保护及本地测试服务会按已保存停留时长保留展示时间，同时继续受服务本身的最长运行时间限制。

可预览应用内和跨应用弹窗，使用已保存样式；均不调用API、不写聊天或关系。悬浮窗需系统权限，后台会保留系统通知或在悬浮窗不可用时使用通知。系统是否弹出顶部横幅仍取决于通知通道和厂商设置。权限状态刷新不会清空未保存的设置输入。

## 数据与验证

旧模式、时间、间隔、声音、振动、宽度及位置首次读取时保留。新配置存于本机SharedPreferences，原包名、原签名覆盖升级会保留。恢复默认参数只填写表单，保存后生效，不自动开启功能。当前聊天加密备份不包含这组本机偏好及请求账本；SQLite和聊天备份仍v11。
