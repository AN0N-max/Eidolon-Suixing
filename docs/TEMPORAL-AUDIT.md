# 时间感知改造：现有源码审计与实施边界

基线：现有Android 1.13源码，不重拉项目。2026-10-30。角色时区按用户确认默认沿用现有设置，允许独立覆盖；每日检查仍为03:00。

## 已核实的数据链

ScheduleEngine.generate保存每日行程；ScheduleRuntime.state每次从ScheduleStore读取当日与昨日，ScheduleData.status按传入时间查询活动。WebActivity.generatePending和ReplyFallback.generate都把ScheduleRuntime.prompt追加到最终聊天system。ReachExecution亦注入日程，且在生成前、生成后重新检查作息/免打扰/有效期和会话变化。因此“日程仅展示、完全没进入模型”不成立。

ModelClient.buildRequest裁剪的是history的完整回合（24000字预算），没有裁剪system。MessageTime.context追加进首个system，保留历史消息时间。未发现日程被程序直接覆盖的证据；但system末尾还有关系场景、申诉、剧情与记忆，存在来源冲突，需要明确分层，不能把潜在模型关注问题当成已证实根因。

## 明确缺口

1. 前台/后台最终回答以contactAt/p.lastAt（用户发消息的时间）调用ScheduleRuntime.prompt，而分析请求、网络等待可能已经耗时；生成/预计投放的时刻未明确区分。延迟规则在回答生成之后才计算，生成时不知道预计投放状态。
2. ScheduleData.zone仅读取producer.timeZone或设备时区。角色、用户、通知免打扰、每日额度共用/混用时区；不能只给prompt换时区而不改日程生成、查询、延期与主动窗口。
3. ScheduleData.status将排定活动直接映射activity/asleep/bath；这对旧的延迟规则有用，但作为实际生活事实过强。ScheduleRuntime.describe对洗澡还直接预断“回复时已经洗完”，对睡眠直接说“消息刚把你叫醒”，缺少证据/投放时间验证。
4. 没有统一注入式Clock。ProducerProfile.prompt使用ZonedDateTime.now；ScheduleRuntime与调度多处System.currentTimeMillis。不同参考片段可取不同时间。
5. 跨会话/跨日互动间隔没有专用计算；有历史消息时间，但没有排除本批新消息后的上次真实互动查询。
6. 没有独立实际模拟状态及版本、有效期和来源，也没有临时事件覆盖的统一存储契约。现有wakeFirst/wakeLast仅在正式回复投放时根据发送时间更新，不能覆盖完整生活状态。
7. 写作事件writing_events只有日期和body，不能伪造分秒时间；长期记忆/Notebook事件有各自的来源语义，不能把它们都视为“今天实际发生的生活事件”。
8. 模型输出后的正式投放事务会提交关系、记忆、约定、写作事件等，并更新叫醒记录；不应从模型随口说的生活描述自动推断实际事件已发生。

## 最小侵入实施顺序

先建立纯时间推导模块与可注入Clock，统一构建请求时刻、角色时区、计划活动的绝对起止与进度；把实际状态、过去未执行的计划和已确认事件明确分离。未知精力/情绪保留unknown/null，不凭空给65分。持久化按需推进记录只能记录“推导过”，不能把漏执行时段写成已完成经历。

角色时区必须同时覆盖日程生成/查询、跨夜作息、延迟回复与主动可用窗口，保留制作人时区用于用户日期和免打扰。需要为已有无时区标记的日程建立迁移/失效规则，避免仅重解释同一个日期造成重复生成或错误搬动行程。

延迟回复必须在正式回答请求前冻结本批预计投放时间（不重复抽随机值），同时提供收到消息、生成、预计投放三个时点；到期后再核对状态变化，不能无条件再次调用模型重写收费。

临时事件只接受有来源、明确有效期的持久化记录；过期覆盖失效，时钟回退标记不确定，不倒退重放事件；长离线仅重算当前时刻、不逐小时请求模型。

## 验证层级

纯规则测试覆盖活动起止、睡眠准备、午夜、跨24小时、连续聊天、夏令时gap/fold、时钟回退、时区变更和重启。实际请求集成测试必须检查前台/恢复/主动三条路径，以及长system/history裁剪后的最终HTTP请求。

假模型测试可证明最终请求被模型端接收、回复经过同一解析/投放路径；不能证明真实服务模型的自然表达。真实最终回复评估需明确服务、模型及有限调用预算；现有工作约束不允许擅自使用手机密钥或触发真实收费API。不得用只回显JSON的mock宣称自然时间感已验收。
